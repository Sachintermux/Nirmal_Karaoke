# Nirmal Karaoke v19 — Smooth Stereo / Anti-Cut Transport

## Root cause addressed
Earlier releases focused on removing a fixed receive delay but also disabled redundant audio packets. That made continuous stereo music sensitive to short packet loss. The receiver also had no hysteresis-based response to changing network conditions.

## v19 architecture
- LiveKit SFU remains the media transport.
- Admin and audience clients use `singlePeerConnection: false` so publishing and subscribing use separate RTP peer connections when supported.
- Host program audio: stereo Opus, 128 kbps ceiling, high priority, DTX off, RED on.
- Audience camera is deliberately low bandwidth (90 kbps max) and host camera is capped at 250 kbps.
- Audience remote program audio is attached through LiveKit's `RemoteAudioTrack` API.
- Receiver adaptive playout target: 100 ms normal, 160 ms moderate degradation, 240 ms severe degradation. The controller uses interval packet loss + jitter, EWMA smoothing, and hysteresis so it does not oscillate.
- During degraded conditions the audience client asks LiveKit for the LOW host-camera layer to protect the music stream.

## Why RED is enabled
LiveKit documents RED (redundant audio data) as a mechanism for recovering from packet loss and recommends enabling it when audio glitches are unacceptable.

## Why not use zero jitter
LiveKit's current zero-jitter mode is available in the Rust SDK and is video-oriented; disabling audio playout buffering in a variable network would trade smoothness for more underruns.
