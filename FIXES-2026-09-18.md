# Nirmal Karaoke LiveKit fixes — 2026-09-18

## v4 fixes
- Fixed **Hear audience audio on admin**: remote audience microphones are now attached through LiveKit's supported audio-element playback path and remain completely outside the host program/Web Audio mix. Monitoring is off by default and can be enabled from the admin Audience panel.
- Admin can now **Share admin camera**. The admin camera is published as a separate LiveKit camera track and is shown locally in the admin stage plus to all audience participants.
- Audience video stage now shows **ADMIN + audience cameras side-by-side**. The admin card is kept first in the grid.
- Admin video stage also shows **ADMIN + audience cameras side-by-side**.
- Admin guest mute now mutes the local admin monitor without changing the host program audio. The audience receives the force-mute signal independently.
- Added a more reliable audience reconnect path: after an unrecoverable disconnect, the audience page requests a fresh LiveKit token and reconnects automatically with exponential backoff.
- Increased access-token TTL from 2 hours to 24 hours. LiveKit token expiration applies to initial connection/reconnection handling; the client also has an automatic fresh-token reconnect path.
- Host token creation now explicitly configures the LiveKit room with a 24-hour empty-room timeout, 120-second departure grace period, and a 100-participant limit when the room is first created.
- Restored/clarified **Remove original vocals** for the current playing music. It uses stereo center-channel cancellation; the optional Guide vocal level now defaults to 0%, so enabling the remover gives an instrumental-first result unless the user deliberately raises the guide vocal.

## Audio isolation rule
Audience microphones are never connected to the host program `MediaStreamDestination`. Admin monitoring is a separate local playback path. This prevents audience audio from being published twice and reduces the chance of speaker/monitor loopback when Windows monitor/system-audio capture is used.

The switch therefore called undefined methods and immediately reset itself.
- Reworked audience monitoring to use LiveKit's documented `RemoteAudioTrack.attach()` + HTMLAudioElement playback path, instead of creating a second Web Audio graph from the remote MediaStreamTrack.
- The admin switch now directly invokes `room.startAudio()` from the user-triggered change event, then plays all currently subscribed audience microphones.
- New audience microphones are automatically played when monitoring is enabled.
- Turning monitoring OFF pauses/mutes all audience audio locally on the admin and leaves the audience tracks available in LiveKit.
- Audience monitoring never connects to the host program MediaStreamDestination, so it is not intentionally rebroadcast.

# v12 Core Rebuild

The LiveKit path was rebuilt instead of layering another monitor patch. The previous admin monitor depended on fragile microphone source/name classification and a custom remote-media playback path. v12 treats remote non-host audio publications as audience microphones, subscribes them explicitly, and uses LiveKit's supported `RemoteAudioTrack.attach()` + browser playback unlock. The token endpoint is unified for Netlify and the local Express server. Host rooms use token room configuration so Go Live does not wait on a separate Room Service list/create API call. Audience pages no longer subscribe to other audience microphones, reducing feedback risk.


## v12 transport decision
The token path no longer calls LiveKit Room Service `listRooms/createRoom` during every join. The host token embeds RoomConfiguration for the first room creation, keeping Go Live independent of Room Service availability. LiveKit documents that rooms are automatically created when the first participant joins and that token room configuration is applied when the room is first created.


## v14 core repair notes
The repeated audience-monitor failure was traced to a combination of event-order/autoplay problems and fragile remote-track handling. The v14 monitor no longer waits for the karaoke DSP graph, uses a dedicated local AudioContext, unlocks that context plus LiveKit playback from the admin click, explicitly subscribes to remote audience audio, and handles `TrackSubscribed` as the ready event. HTML audio remains a fallback only.

Go Live was also simplified so the browser first connects to the room directly using a signed access token. Program audio publication remains a separate, retryable step. The token function no longer imports `@livekit/protocol` or constructs `RoomConfiguration`, removing a serverless-runtime dependency from the critical Go Live path.


## v15 — audience-to-admin audio core repair
- Removed the custom admin Web Audio receive graph from the audience-monitoring path.
- Admin audience microphones now use the canonical LiveKit `RemoteAudioTrack.attach()` -> HTMLAudioElement path.
- Added a dedicated trusted-gesture method that calls `room.startAudio()` immediately from the admin monitor button and immediately attempts to play already-subscribed audience microphones before any asynchronous subscription reconciliation.
- Remote microphone audio elements remain attached and muted while monitoring is OFF, then are unmuted/played when monitoring is enabled. New `TrackSubscribed` microphones inherit the enabled state.
- Added `AudioPlaybackStatusChanged` recovery so a browser that reports audio playback becoming allowed later will automatically resume the admin monitor.
- Kept audience monitoring completely outside the host program `MediaStreamDestination`; it is admin-speaker playback only.
- Removed `await prepareConnection()` from Go Live; connection preparation is now best-effort and non-blocking so it cannot delay/kill the primary `room.connect()` path.

## Stereo audio mode
- LiveKit host program audio now uses `musicHighQualityStereo`/`musicStereo` with `forceStereo: true`, `dtx: false`, and `red: false`.
- The Web Audio master/output buses are explicitly 2-channel before the LiveKit MediaStreamDestination.
- System/display audio capture requests 2 channels at 48 kHz and feeds a stereo output bus; mono capture providers are upmixed to L/R rather than published as a one-channel LiveKit track.
- Audience microphone capture requests 2 channels and is published with LiveKit stereo options. Physical mono microphones may contain identical L/R content, but the transport remains stereo.


## v17 stereo transport hardening
- Final Web Audio destination is constructed/configured as explicit 2-channel discrete stereo.
- Final L/R splitter/merger pins left and right independently before the LiveKit WebRTC source.
- System audio capture requests 48 kHz / 2-channel input with echo cancellation disabled for music fidelity.
- Audience playback now uses LiveKit RemoteAudioTrack.attach() instead of wrapping the remote MediaStreamTrack manually.
- Versioned module URLs (`?v=18`) force browsers to load the corrected transport code after deployment.
- Host and audience expose runtime channel-count diagnostics so a true MONO source is visible instead of being mislabeled as stereo.


# v18 — smooth stereo transport
- Removed the forced 10 ms remote audio playout/jitter target. LiveKit's adaptive platform default is used instead; the 10 ms target could cause underruns/cuts on mobile and variable Wi-Fi.
- Reduced host program stereo Opus ceiling from 128 kbps to 96 kbps while keeping `forceStereo: true`, DTX/RED off, and high RTP priority. This reduces network pressure while retaining stereo music quality.
- Lowered admin camera bandwidth and audience camera bandwidth/framrate, with audio marked high priority and video low priority, so video cannot consume the room's available bandwidth at the expense of program audio.
- Simplified audience playback AudioContext: remote program audio remains direct LiveKit HTMLAudio playback without an unused second compressor graph.
- Switched host audio-engine scheduling from `interactive` to `balanced` to reduce producer-side audio underruns under DSP load.
- Added receiver stream-state diagnostics for paused remote audio tracks.


# v18 — smooth stereo program playback
- Removed the forced 10 ms `setPlayoutDelay()`/`jitterBufferTarget` override on the audience receiver and returned to LiveKit/browser adaptive audio playout.
- Reduced program stereo Opus ceiling to 96 kbps with high RTP priority; reduced camera bandwidth to protect audio.

- Final v18 tuning further lowers the admin camera to 640×360/450 kbps and audience cameras to 240×180/120 kbps so multiple camera feeds are less likely to compete with the 96 kbps stereo music track.
